# P0 实施与验收手册（待执行）

## 目的
证明官方原生虚拟摄像头路径在目标 Windows 11 上能注册、激活和持续发送动态测试帧。P0 不采集物理摄像头、不启动 Python UI。首先复现官方基线，然后使用独立产品 CLSID 与名称进行最小改动。

## 执行顺序
1. 在专用测试机记录 OS edition/build、x64、相机隐私设置、用户/提升身份、SDK、VS 工具集。确认 mfvirtualcamera.h 及 API 导出，不根据系统名称判断兼容性。
2. 获取完整微软 Windows-Camera 仓库到 third_party，记录确切 SHA，检查共享工程依赖和许可证。按该版本官方说明构建 Release x64 媒体源及测试；记录额外开发依赖，不能将 UWP 管理器当作产品运行时要求。
3. 使用官方安装流程建立对照。确认 DLL 依赖完整、受保护路径、64 位 COM 注册正确；在测试进程内激活成功后，再验证系统 FrameServerMonitor/FrameServer 路径。前者不证明后者成功。
4. 产品 manager 使用独立 CLSID，调用 MFCreateVirtualCamera 配置 Session/CurrentUser，Start 后记录设备 symbolic link，进程保持运行。在会话模式下管理器提前退出导致设备消失属于预期行为。
5. 独立 MF 读取器按 symbolic link 选择设备，列举真实媒体类型，连续获取至少 300 帧。检查大小/stride、frame hash 的变化、时间戳单调和采样持续时间；不能仅截图设备列表。
6. 微软示例适用的媒体源测试与虚拟摄像头测试分别执行；不把直接加载 DLL 的测试结果当作服务端激活通过。
7. 对四款客户端逐个测试：彻底退出→重开→选择产品设备→本地预览→第二台设备/账号实际接收→观察移动标志/帧号至少 60 秒。需要登录的操作保留给有账号的人，不能以测试无法登录为兼容通过。
8. 完成生命周期、权限和清理测试，最后移除本次创建的设备和注册项，确认其他摄像头未受影响。

## 诊断次序
API 不存在→OS/SDK；Create/Start 拒绝→隐私、scope、实际调用身份；类未注册→64 位 CLSID/路径；模块缺失→DLL 依赖；进程内正常但服务异常→服务身份/文件访问/服务端日志；设备可见黑屏→媒体类型、事件、采样请求、时间戳；只有一个客户端异常→记录该客户端类型协商与重开行为。
日志记录失败阶段与 HRESULT 十六进制值，不把所有 E_ACCESSDENIED 都提示为“请管理员运行”。

## 证据模板
日期、操作者、机器 ID、OS build、CPU/GPU、SDK/工具集、仓库 SHA、产品版本、DLL hash、设备参数、调用身份、媒体类型、客户端版本/架构、具体步骤、预期、实际、HRESULT、日志路径、脱敏截图/第二端确认、结论。
